# substrate-gke Terraform module

The Terraform face of the installer wizard. Its inputs are the wizard's own:
each variable is a value one of the wizard's screens asks for, with the same
default (what pressing enter does) and validated by the same rules. See
[INPUTS.md](INPUTS.md) for the list.

It does what the wizard does after its questions:

1. **GCP resources**, as Terraform resources (`gcp.tf`), mirroring setup-gcp's
   bootstrap: the GKE cluster (Workload Identity, the PodCertificate beta APIs,
   Dataplane V2, GKE's Filestore driver off) and its node pool (nested
   virtualization for micro-VMs, Substrate's sysctls, autoscaling), the
   snapshot bucket, the Artifact Registry repository for a source build, and
   the IAM grants for the nodes, atelet and ate-api-server. With
   `create_cluster = false` it uses an existing cluster as is, and fails the
   plan with the command to run if that cluster lacks Workload Identity or the
   beta APIs.
2. **The Substrate control plane** (`install.tf`), as two Helm releases of
   charts generated from the Substrate project's own manifests at the pinned
   commit (`charts/substrate-crds`, then `charts/substrate`; see
   `installer/internal/chartgen`): everything `ate-setup deploy ate-system`
   applies with pre-built images. What ate-setup does imperatively is done
   around the charts: the five key pools are generated with Terraform's `tls`
   provider and passed in as values (the private keys are in Terraform state;
   the CAs last 365 days, as ate-setup's do); the `ate.dev/substrate-version`
   node label is set on the node pool (an existing cluster's unlabelled nodes
   are labelled by `scripts/substrate.sh label-nodes`); and the bundled
   Postgres setup runs from the StatefulSet's postStart hook. A build from
   source still runs `ate-setup`, since it pushes images.
3. **The rest of the install**, as `terraform_data` steps running
   `scripts/substrate.sh` on the machine running Terraform, because none of it
   is Kubernetes objects a chart can own: the Filestore CSI overlay (a git
   clone and deploy script), the micro-VM assets and SandboxConfig when
   `sandbox_class = "microvm"` (assembled and staged into the bucket by
   upstream's `hack/install-microvm-deps.sh`), and the counter demo (its
   ActorTemplate is created through ate-api-server).

The caller configures the `helm` provider against the cluster the module
outputs (`cluster_endpoint`, `cluster_ca_certificate`); see
`terraform/example`. The script steps need bash, gcloud (logged in, with
application-default credentials), kubectl, git and go on the machine running
Terraform; docker for a source build; and sha256sum, zstd, unzip, jq and make
for micro-VM. Set `install_substrate = false` to stop after the GCP resources.

The releases set `take_ownership`, so a cluster the wizard installed onto can
be moved under Terraform; its key pools are then replaced, which rotates the
CAs.

Deliberate differences from the wizard: the APIs are left to the caller (the
example enables them), and the managed OpenTelemetry config and monitoring
dashboards are not created. An install step re-runs when what it was run with
changes, not when the cluster drifts; `terraform apply -replace` forces one.
`terraform destroy` deletes the cluster; the bucket only goes too with
`bucket_force_destroy = true`, since it holds snapshots.

```hcl
module "substrate" {
  source     = "github.com/ai-on-gke/substrate-gke//terraform/modules/substrate-gke?ref=<release>"
  project_id = "my-project"
}
```

Requires Terraform 1.9 or later: some rules read other variables (a field only
the pre-built track asks for is only required when `image_source = "prebuilt"`).

## Which files are generated

| File | Owner |
|---|---|
| `variables.tf`, `options.tf`, `defaults.tf`, `INPUTS.md` | generated by `installer/cmd/tfgen` from the declarations; do not edit |
| `versions.tf`, `locals.tf`, `gcp.tf`, `install.tf`, `outputs.tf` | generated by `tfgen` from `installer/internal/tfgen/templates/*.tf.tmpl`, `tfgen.GCP` and `chartgen`'s key pools and images; do not edit |
| `charts/` | generated by `tfgen` (`installer/internal/chartgen`) from the Substrate project's manifests at the commit the installer pins; do not edit |
| `scripts/substrate.sh`, this README | hand-written |

`make generate` renders the charts from a checkout of the pinned Substrate
commit, which it fetches into the user cache the first time (git and network
needed); `go run ./cmd/tfgen -substrate DIR ..` uses one you already have.
Bumping the pin (`installer/internal/snapshot`) and regenerating moves the
charts to the new manifests. chartgen checks every substitution it makes and
fails if the upstream manifests stop matching, rather than emitting a chart
that quietly differs from ate-setup's install.

`variables.tf` holds the wizard's inputs; `options.tf` the few Terraform-only
settings (`install_substrate`, `substrate_work_dir`, `deletion_protection`,
`bucket_force_destroy`), declared in `installer/internal/tfgen/options.go`.

## How it stays in sync

The inputs are declared once, as plain data, in
[`installer/internal/inputs/spec.go`](../../../installer/internal/inputs/spec.go).
That package knows nothing about Terraform: each rule is a kind ("required",
"matches this pattern", ...) plus parameters, with a Go check. Everything
Terraform-specific lives in `installer/internal/tfgen`, which translates each
rule kind (and each named custom check) into HCL; the installer itself never
imports it.
`tfgen` renders it into `variables.tf`: one variable per input and one
`validation` block per rule, with defaults read from the same Go constants the
wizard uses (the release pin, `state.NewSetup`, and so on), so bumping the pin
moves the module's defaults too.

The wizard's screens still build their own fields and checks: the tooling was
added without changing the installer's existing code. Until the screens read
the declarations too, tests (run by `make test`) keep the copies in step:

- `installer/internal/ui/inputs_parity_test.go` drives the real screens
  (project, images, cluster name, autoscaling bounds) and requires their
  labels, placeholders, character limits, starting values and verdicts to
  match the declarations, including which field gets blamed.

- `TestGeneratedFilesAreUpToDate` fails when the committed files differ from
  what the declarations render to. `make verify` runs the same check.
- `TestTerraformConformance` runs every case in `installer/internal/tfgen/tfgen_test.go` through both
  `inputs.Validate` and `terraform plan`, and requires the same inputs to fail
  with the same messages. `TestEveryRuleHasAFailingCase` requires a case for
  every rule, so no rule's HCL goes unchecked. It skips when `terraform` is not
  on `PATH`; set `SUBSTRATE_REQUIRE_TERRAFORM=1` in CI to make that a failure.
- `TestTerraformDerivations` holds `locals.tf` to the Go it mirrors (region,
  default bucket name, build repository).
- `TestGCPFactsMatchSetupGCP` holds `tfgen.GCP` (beta APIs, node sysctls,
  initial node count, IAM roles and subjects) to setup-gcp's.

## Adding or changing an input

1. Declare it (or change its rules) in `spec.go`, in wizard order. Prefer the
   existing rule kinds (`required`, `matches`, `oneOf`, `between`, ...), which
   `tfgen` already translates; a new custom check needs its Go check in
   `inputs` and its HCL in `tfgen`'s `customHCL`
   (`TestEveryCustomCheckHasHCL` fails until it has one).
2. Make the same change on the screen; the parity tests fail until the two
   agree.
3. Add cases to `installer/internal/tfgen/tfgen_test.go`: at least one that fails each new rule, and
   the edges that should pass.
4. Run `make generate` and commit the regenerated files with the change.

## Not inputs

Some of what the wizard asks is a decision about what a live probe found,
not configuration, and has no variable: tearing down an existing install,
staging micro-VM assets on a cluster without KVM, acknowledging a permission
warning, enabling the GKE API. The welcome screen's track only hides the
advanced fields, whose defaults then apply. The upgrade track touches nothing
in GCP and is out of scope.
